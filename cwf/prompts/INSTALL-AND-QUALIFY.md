# Fresh local opencode prompt: install and qualify CWF

Use the following prompt in a new opencode terminal or IDE session on the target Mac. Provide the absolute path of the extracted `cwf-0.1.0` directory. Submitting this prompt authorizes the local installation described below; the ZIP alone does not.

---

Install and independently qualify the Contextual Work Framework from the extracted bundle I supplied. Work from actual local evidence; assume no access to the conversation that created it.

Read README.md, docs/OPERATIONS.md, docs/DEVIATIONS.md, docs/VALIDATION.md, and docs/PLATFORM.md. Consult docs/SPECIFICATION.md and schemas only when needed. The goal is a global per-user capability across repositories and outside repositories, preserving my personalized opencode setup. Ticketing, ICM, quiz, Feynman, background workers, and hooks are not dependencies.

1. Identify macOS version/architecture, available Python 3.11+, Git, the opencode version and surfaces in use, actual home and opencode config directory (`opencode debug paths config`), global instruction file, existing skills and skill permission rules, and any managed restrictions. Check current official documentation for any behavior that differs from the bundle's assumptions. Do not change model/provider settings, permissions, existing plugins, or Git configuration. Do not install missing prerequisites without authorization.
2. Inspect the installer code enough to understand owned targets, planning, rollback, and limitations. Run the automated suite with disposable homes/repositories. Record actual passes, failures, and skips. Do not count Linux authoring evidence as macOS evidence.
3. Perform a disposable-home install, doctor, launcher check, disable/enable, uninstall, and recovery/rollback test. Keep existing personal files in the fixture and verify their preservation. Do not use my real repositories as destructive test fixtures.
4. Generate a live install plan. Inspect its changes and conflicts. Apply it if it matches the documented scope and this authorization. For material collisions, policy restrictions, unexpected writes, or failed required tests, preserve the plan and stop only the affected deployment actions; report the specific blocker. Do not overwrite unrelated files, delete existing skills, or weaken permissions to proceed.
5. Verify owned release/launcher/skill links and effective activation block. Confirm actual discovery in fresh terminal and IDE sessions. If only one surface is available, qualify that surface and label the other untested. Do not claim a model saw a skill based solely on its path existing.
6. Run relevant scenarios in docs/PILOT.md using disposable copies. Include plain unticketed requests, the widget example, intentionally separate similar logic, documentation conflicts, an unticketed batch, interrupted work, and unrelated everyday questions inside a repo. For activation tests, do not explicitly name the skill; keep explicit-invocation tests separate. Record failures and uncertainty, not just successful examples.
7. Explain how to disable a domain/the whole framework, rollback, and uninstall. Preserve local state by default. Do not upload prompts, source code, receipts, or observations. Provide a concise report with exact tested versions, installation outcome, test evidence, unresolved issues, and supported versus untested configurations. If measurements are unavailable, mark them unavailable rather than estimating tokens or savings.

Continue through these steps without routine confirmation requests. Ask only if a missing decision materially changes installation scope or necessary authority. Do not claim production readiness from installation success alone.
